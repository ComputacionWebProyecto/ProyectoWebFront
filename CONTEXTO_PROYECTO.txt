¿QUÉ ES ESTE FRONTEND?
----------------------
Es un editor visual de procesos de negocio estilo BPMN (Business Process Model 
and Notation) construido con Angular 18+ (standalone components). Permite a las 
empresas diseñar, visualizar y gestionar flujos de trabajo mediante un canvas 
SVG interactivo tipo drag-and-drop.


================================================================================
COMPONENTES PRINCIPALES DEL MODELO BPMN
================================================================================

1. ACTIVITY (Actividad) - Rectángulo azul
   ----------------------------------------
   - Representa una tarea o acción en el proceso
   - Tiene nombre, descripción, posición (x,y), dimensiones (width, height)
   - Se asigna a un Role (quién la ejecuta)
   - Pertenece a un Process (flujo completo)
   - Se puede mover, redimensionar, conectar con otras actividades o gateways

2. GATEWAY (Puerta de enlace) - Diamante
   ---------------------------------------
   - Representa puntos de decisión o bifurcación en el flujo
   - Tipos: decision-gateway (?), parallel-gateway (+), exclusive-gateway (X)
   - Tiene posición (x,y) fija (sin dimensiones)
   - Se conecta con Activities o con otros Gateways

3. EDGE (Conexión/Flecha) - Línea con flecha
   ------------------------------------------
   - Conecta dos nodos: Activity→Activity, Activity→Gateway, Gateway→Activity, 
     Gateway→Gateway
   
   SISTEMA NUEVO (tipado): 
     - fromType, fromId, toType, toId
   
   SISTEMA LEGACY (compatibilidad): 
     - activitySourceId, activityDestinyId (solo Activity→Activity)
   
   - Tiene etiqueta opcional (label) y descripción
   - Renderizado SVG con path curvo

4. PROCESS (Proceso) - Contenedor lógico
   --------------------------------------
   - Agrupa Activities, Gateways y Edges
   - Pertenece a una Company
   - Un usuario puede tener múltiples procesos activos

================================================================================
BACKEND SPRING BOOT - ENDPOINTS
================================================================================

ActivityController (/api/activity)
-----------------------------------
POST   /api/activity           → crear Activity (body: ActivityDTO sin id)
PUT    /api/activity           → actualizar Activity (body: ActivityDTO con id)
GET    /api/activity           → listar todas las Activities
GET    /api/activity/{id}     → obtener Activity por ID
DELETE /api/activity/{id}     → eliminar Activity

GatewayController (/api/gateway)
---------------------------------
POST   /api/gateway           → crear Gateway
PUT    /api/gateway           → actualizar Gateway (body con id, NO /{id} en URL)
GET    /api/gateway           → listar todos
GET    /api/gateway/{id}     → obtener por ID
DELETE /api/gateway/{id}     → eliminar

EdgeController (/api/edge)
---------------------------
POST   /api/edge              → crear Edge/conexión
PUT    /api/edge              → actualizar Edge (body con id)
GET    /api/edge              → listar todas
GET    /api/edge/{id}        → obtener por ID
DELETE /api/edge/{id}        → eliminar

⚠️ IMPORTANTE: 
El método PUT en los tres controladores espera el body con el campo id incluido, 
NO usa /{id} en la URL (excepto GET y DELETE).

================================================================================
FLUJO DE TRABAJO ESPERADO
================================================================================

Usuario en Dashboard (localhost:4200)
    ↓
Crea Activity → activityService.create(payload)
    ↓
POST http://localhost:4200/api/activity (proxy intercepta)
    ↓
Proxy redirige → http://localhost:8080/api/activity
    ↓
Spring Boot Controller procesa, guarda en DB, devuelve ActivityDTO con id
    ↓
Frontend recibe respuesta → tap() actualiza BehaviorSubject store
    ↓
Todos los componentes suscritos a list$ reciben el nuevo estado
    ↓
Dashboard renderiza la Activity en el canvas SVG

PATRÓN DE SERVICIO HTTP + CACHE REACTIVO
================================================================================

Ejemplo: ActivityService
-------------------------

@Injectable({ providedIn: 'root' })
export class ActivityService {
  private readonly httpBaseUrl = '/api/activity';
  private readonly store = new BehaviorSubject<Activity[]>([]);
  readonly list$ = this.store.asObservable();

  constructor(private http: HttpClient) {
    this.loadFromBackend();  // Carga inicial automática
  }

  // CREATE
  create(payload: Omit<Activity, 'id'>): Observable<Activity> {
    return this.http.post<Activity>(this.httpBaseUrl, payload).pipe(
      tap(created => {
        const current = this.store.value;
        this.store.next([...current, created]);  // Actualiza cache local
      })
    );
  }

  // UPDATE
  update(activity: Activity): Observable<Activity> {
    return this.http.put<Activity>(this.httpBaseUrl, activity).pipe(
      tap(updated => {
        const current = this.store.value;
        const index = current.findIndex(a => a.id === activity.id);
        if (index !== -1) {
          const newList = [...current];
          newList[index] = updated;
          this.store.next(newList);  // Actualiza cache local
        }
      })
    );
  }

  // DELETE
  delete(id: number): Observable<void> {
    return this.http.delete<void>(`${this.httpBaseUrl}/${id}`).pipe(
      tap(() => {
        const current = this.store.value;
        this.store.next(current.filter(a => a.id !== id));  // Actualiza cache
      })
    );
  }

  // GET BY ID
  getById(id: number): Observable<Activity> {
    return this.http.get<Activity>(`${this.httpBaseUrl}/${id}`);
  }

  // LOAD ALL
  private loadFromBackend(): void {
    this.http.get<Activity[]>(this.httpBaseUrl).pipe(
      tap(activities => this.store.next(activities))
    ).subscribe({
      next: () => console.log('[ActivityService] Activities loaded'),
      error: (err) => console.error('[ActivityService] Error:', err)
    });
  }
}

VENTAJAS DE ESTE PATRÓN:
------------------------
1. Cache local reactivo: todos los componentes se suscriben a list$
2. Sincronización automática: tap() actualiza el cache tras cada operación HTTP
3. Un solo punto de verdad: BehaviorSubject mantiene el estado centralizado
4. Optimización: evita requests redundantes, los componentes leen del cache
5. Reactividad: cuando el store cambia, todos los suscriptores se actualizan

CONFIGURACIÓN DEL PROXY
================================================================================

Archivo: proxy.conf.json
------------------------
{
  "/api": {
    "target": "http://localhost:8080",
    "secure": false,
    "changeOrigin": true,
    "logLevel": "debug"
  }
}

Archivo: package.json (script modificado)
-----------------------------------------
"scripts": {
  "start": "ng serve --proxy-config proxy.conf.json",
  ...
}

CÓMO FUNCIONA:
--------------
1. Frontend corre en localhost:4200
2. Backend corre en localhost:8080
3. Cuando frontend hace: http.get('/api/activity')
4. El navegador intenta: http://localhost:4200/api/activity
5. Angular Dev Server intercepta la request (gracias al proxy)
6. Reenvía a: http://localhost:8080/api/activity
7. Recibe respuesta del backend
8. La devuelve al frontend
9. NO HAY ERRORES DE CORS (misma origin para el navegador)
